# 0003. Identity is per machine, with `owner` as a soft label

- **Status:** accepted
- **Date:** 2026-09-17

## Context

Mail needs an addressee. The obvious unit is the person — "send this to
Matthew" — but the thing that actually holds a keypair, runs a daemon, listens
on a port and can be authenticated is a machine. Matthew has a desktop and a
laptop, and a Claude Code session on each.

Making identity per person means either a shared private key across machines (a
key on every laptop, revocable nowhere) or an account system that decides which
machines belong to whom — and SPEC §1 rules out accounts.

Making identity per machine means addressing gets less convenient unless
something bridges the gap.

## Decision

One Ed25519 keypair per machine, generated by `hivemind init`. The `NodeId` is
the SHA-256 fingerprint of the node's DER-encoded self-signed certificate,
shown to humans as `hm1:<base32-lower>` with an 8-character short prefix
(SPEC §6.1).

`owner` is free text attached to a node — a label, not an identity. A recipient
of `matthew` expands at send time to every paired peer whose `owner` is
`matthew` (SPEC §8). Nothing verifies that claim.

## Consequences

- The thing we authenticate is the thing that exists. The TLS peer certificate
  *is* the identity; pinning it by fingerprint needs no CA, no hostnames and no
  directory (SPEC §6.3).
- Losing a laptop revokes exactly one identity: remove that peer from
  `peers.toml` on each machine. No key rotation across a fleet.
- Addressing stays human: `hivemind send matthew` reaches all of Matthew's
  machines, and `hivemind send matthew-mbp` reaches one.
- `owner` is unauthenticated and must never be treated as a security boundary.
  Any node can claim any owner string. This is acceptable because the trust
  decision already happened at pairing: you confirmed *that machine's*
  fingerprint by hand, and the owner label only affects fan-out among peers you
  have already trusted. Everything that grants access keys off `NodeId`; nothing
  keys off `owner`.
- Fan-out is computed at send time and the expansion is stored with the message,
  so a machine paired on Tuesday does not retroactively receive Monday's mail.
  The alternative — resolving recipients at delivery time — would make "who was
  this sent to" unanswerable after the fact.
- One person with four machines appears four times in `hivemind peers`. We
  accept the noise; the web UI and CLI group by owner when displaying.
- Pairing is per machine pair, so N machines is N·(N−1)/2 confirmations. For a
  team of a handful of people this is a one-time cost measured in minutes, and
  `--trust-network` exists for LANs where even that is too much (SPEC §6.2).

## Alternatives considered

**One identity per person, key copied between machines.** Addressing is natural
and pairing is O(people). Rejected: a private key that lives in four places
cannot be revoked from any of them, and two machines presenting the same
certificate makes the delivery target ambiguous.

**A person key that signs per-machine subkeys.** Keeps per-machine revocation
and makes `owner` verifiable. Rejected for v1 as a certificate hierarchy we
would have to design, document and get right, for a property — proving an owner
claim — that pairing already covers. The `NodeId` scheme does not preclude it.

**Identity per Claude session.** Rejected: sessions are ephemeral and mail is
not. The daemon outlives every session on the machine, which is the whole point
of store-and-forward.
